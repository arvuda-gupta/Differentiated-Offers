# 1. Understanding & Scope

**Document Purpose**

This page defines the problem space, platform design, offer taxonomy, lifecycle methodology, and success metrics for the Differentiated Offers AI Platform. It serves as the foundational reference for all subsequent design and build decisions.

## Section 1 - Problem Statement

**Context**

Syngenta operates across Crop Protection (CP), Seeds, and Biologicals in European markets. The current state of differentiated offer development is fragmented and must be fundamentally restructured.

### Market Reality

- Syngenta sells CP, Seeds, and Biologicals across Europe.
- **75% of market revenue** derives from standalone products (Foundation/a component). Commoditisation pressure is increasing year-on-year.
- Regulatory loss of active substances is accelerating, narrowing the product differentiation window.
- Growers increasingly expect *outcomes*, not just inputs - this shift demands a new commercial model.

### The Internal Problem

- Current differentiated offer development is **fragmented, inconsistent, and intuition-driven**.
- Approximately **87 offers scattered across Europe** with no shared development process, no shared learnings, and no scaling mechanism.
- Teams routinely *fall in love with solutions* before validating whether genuine customer demand exists.
- There is a weak linkage between: customer needs → offer design → execution → value delivery.

### Field Insight

**What Customers Actually Value**

Field evidence consistently shows that customers value **compliance, simplicity, and defensibility** - not complex innovation for its own sake. Offer design must be anchored to these priorities.

## Section 2 - What This Platform Is

### Platform Definition

The Differentiated Offers Platform is an **AI-powered, agentic platform** that guides commercial teams through the full offer development lifecycle - from initial customer need validation through to scaling proven offers across markets.

**What This Platform Is NOT**

- NOT a chatbot - agents act autonomously using tools and surface insights proactively.
- NOT a form wizard - the platform makes decisions and only pauses when human judgment is genuinely required.

### Three Platform Surfaces

| Surface | Description | Primary Users |
| --- | --- | --- |
| **Workspace** | Per-offer project space where commercial teams build and progress offers through the 6-stage lifecycle | Commercial teams, Agronomy |
| **Library** | Shared Needs Bank + Offer Bank + ConceptBank - the institutional knowledge layer | All users |
| **Dashboard** | Leadership portfolio view with funnel analytics, heatmap, white-space identification, and scoring | Leadership, Marketing |

## Section 6 - The 6-Stage Offer Lifecycle

Every offer progresses through six defined stages. Each stage has a clear goal, defined AI agent role, and a specific human decision gate.

**Design Principle**

Agents act autonomously wherever possible. Humans are only interrupted at genuine decision points - go/no-go gates, approval decisions, and actions that require commercial or strategic judgment that cannot be automated.

### Stage 1 - Discovery

|  |  |
| --- | --- |
| **Goal** | Validate that a genuine, addressable customer need exists before any offer design begins |
| **Key Inputs** | Crop type, country/CU, customer segment type |
| **AI Agent Role** | Discovery Agent pulls from the Needs Bank, surfaces relevant market data and existing competitor offers, and identifies whether this need is already addressed in the portfolio |
| **Human Decision Required** | Confirm and refine the problem statement - is this need real, significant, and unmet? |
| **Output** | Documented need linked to a Needs Bank entry; foundation for Concept Development |

### Stage 2 - Concept Development

|  |  |
| --- | --- |
| **Goal** | Design a differentiated offer concept that passes the differentiation and viability gates |
| **Key Inputs** | Validated need from Stage 1 |
| **AI Agent Role** | Concept Validation Agent runs: (1) differentiation gate - 5 criteria, must meet ≥2 to proceed; (2) duplicate check against ConceptBank; (3) kill filter - 4 criteria, automatic stop if triggered. Agent surfaces scoring rationale. |
| **Human Decision Required** | Go/No-Go on borderline scores where agent confidence is insufficient for automatic routing |
| **Output** | ConceptBank record with component codes, differentiation hypothesis, and gate scores |

### Stage 3 - Offer Validation / MVP

|  |  |
| --- | --- |
| **Goal** | Test the concept with a minimum viable experiment before committing to full launch investment |
| **Key Inputs** | Concept card from Stage 2 |
| **AI Agent Role** | Surfaces MVP card template, recommends validation method (customer interview / focus group / prototype) based on offer type, and provides historical pass rates for similar concepts |
| **Human Decision Required** | Run actual customer conversations - this step requires physical field interaction that cannot be automated |
| **Output** | Validated Prototype DB record with Pass / Reiterate / Stop decision and supporting evidence |

### Stage 4 - First Launch

|  |  |
| --- | --- |
| **Goal** | Execute a structured commercial launch with all readiness criteria verified |
| **Key Inputs** | Validated MVP from Stage 3 |
| **Human Decision Required** | Stage Gate 2 formal approval - commercial leader sign-off required before offer goes live |
| **Output** | Offer enters MRP DB and is published to the live Offer Bank |

### Stage 5 - Scale-Up

|  |  |
| --- | --- |
| **Goal** | Port a proven offer to new markets efficiently, without rebuilding from scratch |
| **Key Inputs** | Live offer from Offer Bank |
| **AI Agent Role** | Scaling Agent builds a candidate brief per target market - identifies markets with the same crop, same pain point, and a gap in the ideal archetype for this offer type |
| **Human Decision Required** | Regional lead reviews and approves the adaptation plan for the target CU |
| **Output** | Adapted offer brief entered into the target CU's pipeline for Stage 1 - 4 fast-track |

### Stage 6 - Post-Launch Review

|  |  |
| --- | --- |
| **Goal** | Annual lifecycle management - ensure portfolio remains relevant and performing |
| **Key Inputs** | Performance data from MRP DB, updated Needs Bank entries |
| **AI Agent Role** | Review Agent generates a structured performance brief with a data-backed Continue / Evolve / Archive recommendation for each live offer |
| **Human Decision Required** | Offer owner makes the final lifecycle decision - Agent recommendation informs but does not replace human accountability |
| **Output** | Updated MRP DB record with new lifecycle status and supporting rationale |

## Section 7 - Success Metrics

| Metric | Definition | Phase 1 (POC) Target | Long-Term Target |
| --- | --- | --- | --- |
| **Platform Adoption** | % of EU commercial teams actively using the platform vs. relying on Excel/PowerPoint workflows | 30 pilot teams engaged | >60% of EU commercial teams |
| **Offer Quality** | % of submitted concepts that pass the differentiation gate (Stage 2) with a qualifying score | Baseline measurement only | >70% pass rate |
| **Time to Launch** | Weeks elapsed from validated customer need (Stage 1 output) to offer going live in Offer Bank (Stage 4 output) | Baseline measurement only | 30% reduction vs. current average |
| **Scale Rate** | Number of offers successfully ported to at least one new market per year via Stage 5 | 0 (Scaling Agent out of scope for POC) | 5+ offers scaled per year |
| **Portfolio Differentiation** | % of EU revenue attributable to non-standalone-product offers (i.e., any offer containing b, c, d, e, or f components) | Baseline measurement only | To be defined at Feb 2026 offsite ambition workshop |
| **Kill Filter Effectiveness** | % of submitted concepts stopped at Stage 2 kill filter before reaching Stage Gate 1 - quantifies wasted investment avoided | Baseline measurement only | >30% of submitted concepts killed early |

## Section 8 - Scope Boundaries

### Phase 1 POC - In Scope

**What We Are Building in Phase 1**

- **Needs Bank** - seeded with import of ~70 validated pain points from existing commercial data
- **Offer Bank** - seeded with all 87 existing European differentiated offers, tagged with component codes
- **ConceptBank DB** - schema defined and ready to receive new concept records
- **Discovery Agent** - Stage 1 automation: needs validation, Needs Bank querying, gap identification
- **Concept Validation Agent** - Stage 2 automation: differentiation gate, duplicate check, kill filter
- **Orchestrator** - coordinates agent handoffs and manages human interruption points
- **Guided Workspace for Stages 1 and 2** - the primary user-facing surface for commercial teams in the POC
- **MVP Card Builder for Stage 3** - structured template and method recommendation for validation experiments

### Phase 1 POC - Out of Scope

**Explicitly Excluded from Phase 1**

- VENUS Databricks live data feed (requires data pipeline work outside this programme)
- Market Intelligence Agent (requires populated Needs Bank/Offer Bank data to be useful - Phase 2)
- Scaling Agent (Stage 5 automation)
- Review Agent (Stage 6 automation)
- Leadership Dashboard (Phase 2 when sufficient data exists to visualise)
- Finance & Trading (e) component full workflow - high compliance complexity requires separate programme
- Carbon/Sustainability (f) full MRV verification workflow - requires integration with third-party verification standards

## Aggregated vs Per-User Data

The platform operates a **hybrid data model**. Understanding which data is shared and which is scoped to a team matters for both the agent design and the privacy model.

| Data | Scope | Rationale |
| --- | --- | --- |
| Needs Bank (70+ pain points) | Shared across all users | Every team benefits from validated pain points collected across all markets. This is the compounding asset of the platform. |
| Offer Bank (87+ scored offers) | Shared across all users | Historical offer performance data is only valuable if every team can see what worked and what didn't across regions. |
| Workspace and in-progress concepts | Per team (workspace-scoped) | Concept development is sensitive commercial work. Teams own their workspace until they choose to publish to the shared ConceptBank. |
| ConceptBank (accepted concepts) | Shared - read. Per-team - write (on ACCEPT) | Teams ACCEPT their own records into the shared bank. Once accepted, all teams can read them to avoid duplication. |
| Prototype DB (MVP test records) | Per team (workspace-scoped) | MVP test data is owned by the team that ran it. Learnings are surfaced by the Scaling Agent in Phase 2 with attribution. |
| MRP DB / Offer Bank (live offers) | Shared - read. Stage Gate only - write | Only offers that have passed Stage Gate 2 enter the live Offer Bank. No team can self-publish a live offer. |

**Phase 1 note:** Cross-workspace aggregation (pattern detection across multiple teams' concurrent work) is a Phase 2 capability (Market Intelligence Agent). In Phase 1, each team's workspace is independent. The shared value comes from the seeded Needs Bank and Offer Bank, not from real-time cross-team signals.
